# 知识提炼与 Markdown 排版

先处理信息，再处理呈现。默认只输出最终 Markdown，不附加分析过程、寒暄或“以下是整理结果”等前言。

## 选择模式

根据用户意图选择一种模式，不要同时执行互相冲突的规则。

| 模式 | 触发信号 | 内容处理 |
|---|---|---|
| 提炼并排版 | 整理笔记、总结、提炼、压缩、去重、重组 | 允许删除、合并和改写，保留原意与关键事实 |
| 仅格式化 | 美化、排版、规范 Markdown、不改内容 | 不增删、不缩写、不改写，只调整 Markdown 与明显错别字 |

意图不明确时：普通文本默认“提炼并排版”；已有清晰结构的 Markdown 默认“仅格式化”。

## 工作流

1. 通读完整输入，识别主题、内容类型、现有结构和目标载体。
2. 选择处理模式；在内部完成内容分析，不额外输出分析文件。
3. 在“提炼并排版”模式下，先执行语义提炼。
4. 从读者视角设计结构，再应用 Markdown 排版。
5. 按 Obsidian、Notion、README 或聊天输出的约束调整结果。
6. 检查事实保真、信息密度、扫描效率和排版一致性。

## 阶段一：语义提炼

仅在“提炼并排版”模式下执行。

### 提取信息

优先保留：

- 结论与核心观点
- 事实、数据与定义
- 因果关系与论证
- 约束、例外与风险
- 决策、状态与行动项
- 理解内容所必需的示例

### 压缩内容

- 按“结论 > 解释 > 示例”组织信息。
- 删除背景铺垫、情绪表达、重复观点、空泛修饰和 AI 套话。
- 合并同义信息，用更短的表达重写，不逐句复述或机械摘抄。
- 保留数字、日期、名称、术语、链接、条件和结论边界。
- 不补充输入中没有的事实、立场、结论或行动项。
- 将“很重要”“必须重视”等情绪性强调直接删除；除非输入明确标注，否则不要将其转换为优先级、状态或风险等级。
- 必须加入推断时，明确标为“推断”或“待确认”。
- 保留必要上下文，使笔记脱离原文后仍能独立理解。

示例：

> 原文：OpenAI 最近发布了新的模型，这个模型拥有更强大的推理能力，同时能够处理更加复杂的任务，因此很多开发者开始关注它。

> 笔记：新模型重点提升推理能力，适合复杂任务。

## 阶段二：结构与排版

先判断读者需要快速看到什么：核心结论、关键数据、概念关系、决策依据、行动项或风险。再选择最小且有效的 Markdown 结构。

### 标题与摘要

- 使用准确、具体、可检索的标题，不使用悬念、夸张或营销式标题。
- 仅在存在明确主题层级时增加标题；避免“第一部分”“内容”“正文”等泛化标题。
- 最多使用一个一级标题；避免只有一个子项的空洞层级。
- 内容较长时，用引用块给出一句话总结；短内容不强制添加。
- 标题或 Frontmatter 已表达主题时，不在正文重复同一句信息。

### Markdown 元素

| 元素 | 适用场景 | 约束 |
|---|---|---|
| 标题 | 主题切换、自然章节边界 | 层级连续，名称具体 |
| 粗体 | 核心结论、关键术语、决策点 | 只强调少量关键信息 |
| 无序列表 | 并列观点、功能、行动项 | 每组最多 7 项 |
| 有序列表 | 步骤、流程、优先级 | 仅用于存在顺序的内容 |
| 表格 | 对比、优缺点、参数、状态、责任分工 | 列之间必须存在稳定对应关系 |
| 行内代码 | 命令、路径、参数、变量和技术术语 | 保留原始字符 |
| 代码块 | 多行代码、配置和命令 | 标注正确语言 |
| 引用块 | 一句话总结、原文金句、重要警告 | 不把普通段落都变成引用 |

不要过度排版：不是每句话都需要加粗，不是每段都需要标题，单一观点不要强塞进表格。

### 列表规则

- 保持列表项语法平行、粒度一致，并按重要性排序。
- 每个列表最多 7 项。
- 超过 7 项时，先合并重复项，再按主题分组。
- 不要为了满足数量限制而删除独立事实。

### 中文排版

- 中文与英文、数字相邻时，按自然阅读需要保留空格，例如“使用 OpenAI 模型”。
- 使用中文全角标点；代码、命令、URL、文件名和原始引用除外。
- 不改动代码块、行内代码、URL 或路径内部的字符与空格。
- 避免标点、空格或换行破坏粗体和链接语法。
- 不使用表情符号作为默认装饰。

## 内容结构

结构是候选模板，不是必填表单。只保留有内容的章节，并根据输入调整名称和顺序。

### 知识类

```markdown
# 主题

> 一句话总结

## 核心概念

## 关键洞察

## 我的理解

## 延伸
```

仅在用户提供个人判断或明确要求分析时使用“我的理解”。仅在输入提供延伸方向或用户明确要求时使用“延伸”。

### 产品分析

```markdown
# 产品

> 产品定位

## What

## Why

## How

## Insight
```

存在多个产品、方案或维度时，优先使用对比表。没有依据时，不自行生成 Insight。

### 技术分析

```markdown
# 技术

> 一句话定义

## Architecture

## Key Points

## Trade-offs

## Use Cases
```

保留代码、命令、接口名和技术术语的原始形式。只有输入涉及架构、权衡或适用场景时才创建对应章节。

## 目标载体

- **Obsidian**：仅在用户要求时添加 YAML Frontmatter、标签或内部链接；不要编造日期、来源或标签。
- **Notion**：默认输出标准 Markdown，不添加 YAML Frontmatter 或 Obsidian 专属语法。
- **GitHub README**：保持标题层级、表格和代码块兼容 GitHub Flavored Markdown。
- **聊天输出**：直接输出最终 Markdown，不生成中间分析或完成报告。

用户提供文件并要求生成新文件时，默认在原目录保存为 `{原文件名}-formatted.md`。不要覆盖原文件，除非用户明确要求。

## 风格约束

- 默认跟随输入语言；输入语言混合或不明确时使用中文。
- 使用简洁、专业、可直接复用的 Notion 或 GitHub README 风格。
- 使用具体名词和动词，避免空泛判断与夸大表达。
- 删除或避免“下面我将介绍”“这是一个非常重要的问题”“随着时代的发展”“值得注意的是”等套话。
- 不重复标题已经表达的信息，不在结尾机械复述全文。
- 在“仅格式化”模式下，即使原文包含套话也不得删除；内容保真优先于风格优化。

## 输出前检查

- 是否选对“提炼并排版”或“仅格式化”模式？
- 开头是否直接给出主题或结论？
- 是否保留了关键事实、限定条件和检索词？
- 是否加入了输入中不存在的事实或观点？
- 标题、表格、列表和强调是否确实提升扫描效率？
- 是否存在超过 7 项且未分组的列表？
- 代码、链接、路径和 Markdown 语法是否保持完整？
- 在“仅格式化”模式下，文字内容是否与原文一致？
- 是否还可以继续压缩或简化排版而不损失含义？
